## Этапы

Работаем без спринтов и дат. Этап — это результат, который можно показать. Этап закрыт, когда сценарий из таблицы работает целиком в `develop`. Задачи следующего этапа можно брать раньше, если их зависимости уже выполнены.

| Этап | Результат |
|---|---|
| 0 | Репозиторий, CI, правила для агентов, выбор LLM-провайдера, требования к оформлению |
| 1 | Регистрация → проект из шаблона → правка `main.tex` → PDF |
| 2 | Загрузил материалы → «сделай отчёт» в чате → PDF; diff и откат правок ИИ |
| 3 | MVP: отчёт по реальным материалам без ручной вёрстки; пилот на 5–10 студентах |
| 4 | Русло 2: «сделай отчёт по ЛР 3» в Claude Code → PDF в папке |
| 5–7 | ВКР: шаблон, импорт DOCX, библиография, проверка преподавателем, diff, нормоконтроль |

Задачи этапов 5–7 описаны крупно и детализируются, когда до них дойдёт очередь.

## Как устроена задача

ID задачи: `<зона><этап>.<номер>`. Зоны: B — бэкенд, F — фронтенд, A — ИИ/MCP, T — шаблоны. Например, `B1.3` — бэкенд, этап 1, задача 3.

**Задача = одна ветка = один PR.** Внутри задачи — список коммитов: агент делает их по порядку, ревьюер читает PR по коммитам.

Поля задачи:
- **Ветка** — имя ветки от `develop`.
- **Зависит от** — что должно быть в `develop` до начала. Если зависимость ещё не готова — работай против заглушки или фейка и договорись с владельцем.
- **Контекст** — какие разделы `architecture.md` прочитать.
- **Коммиты** — сообщения коммитов и что в каждом.
- **Готово, когда** — проверяемые критерии.
- **Не делать** — частые ошибки и выход за рамки.

Размер PR — до ~400 изменённых строк без lock-файлов и сгенерированного кода. Если больше — задачу делим, предварительно обсудив.

## Как берём задачи

- **Доска** (Miro): Бэклог → Можно брать (зависимости выполнены) → В работе → Ревью → Готово. Карточка = ID задачи.
- **Порядок.** Берёшь верхнюю задачу своей зоны из «Можно брать». Задачи, которые блокируют других (список ниже), — вне очереди.
- **Лимит.** В работе у человека — не больше двух задач. Если ждёшь ревью — сам ревьюишь чужое.
- **Результат этапа** показываем команде и руководителю, когда этап закрыт.
- **Вопросы по контрактам** — сразу в общий чат.

## Подготовка рабочего места (один раз)

1. `git config user.name` и `git config user.email`. Email должен быть привязан к твоему GitHub-аккаунту — коммиты агента идут от твоего имени.
2. `git config core.hooksPath .githooks` — включает хук, который вырезает строки об авторстве ИИ.
3. Установить GitHub CLI и выполнить `gh auth login` — через него агент открывает PR от твоего имени.
4. Запустить Claude Code в корне репозитория и подтвердить доверие к папке. Без этого не применяются разрешения из `.claude/settings.json`. Проверка — `/status`: в «Setting sources» есть «Shared project settings».
5. Не включать в личных настройках атрибуцию обратно. `.claude/settings.local.json` и `~/.claude/settings.json` не должны задавать `attribution`.

## Как дать задачу агенту

Новый чат на каждую задачу. Промпт:

```
Задача B1.3 из docs/tasks/backend.md.
Прочитай AGENTS.md, нужные разделы docs/architecture.md и саму задачу.
Сначала покажи план по коммитам из задачи — какие файлы, что в каждом коммите. Код не пиши, пока я не одобрю.
Потом сам создай ветку, делай по одному коммиту (код + тесты → линтер и тесты → коммит) и коротко отчитывайся после каждого.
В конце — /code-review develop...HEAD, исправь находки, запушь ветку и открой PR в develop по шаблону. Пришли ссылку.
Если чего-то не хватает в контрактах или задача противоречит architecture.md — остановись и спроси.
```

## Ревью кода

1. **Агент проверяет себя до PR:** `/code-review develop...HEAD`.
   - Цель указывается явно: без неё ревью сравнивает с удалённой веткой и может пропустить запушенные коммиты.
   - Ревью работает в отдельном субагенте с чистым контекстом и учитывает `CLAUDE.md`/`AGENTS.md`.
2. **PR** открывает агент от имени автора задачи. CI зелёный, включая `no-ai-attribution`.
3. **Ревьюер-человек.**
   - Можно сначала запустить `/code-review <номер PR> --comment` — находки появятся комментариями к строкам от имени ревьюера.
   - Потом читай сам по коммитам. Фокус: соответствие задаче и контрактам, безопасность, понятность, тесты проверяют поведение, а не реализацию.
   - Approve — только если понимаешь каждый коммит. Автор отвечает за каждую строку, даже написанную агентом.
4. **Замечания** автор передаёт своему агенту: «исправь замечания из PR #N», тот коммитит и пушит в ту же ветку.
5. **Merge** делает человек: «Rebase and merge», чтобы атомарные коммиты остались в истории.

Ревьюеры по умолчанию:

| Зона | Ревьюер |
|---|---|
| backend | Бирук |
| ai-mcp | Чистяков |
| frontend | Чистяков; Вершинина смотрит UX |
| templates | Бирук (интеграция с промптами), Чистяков — для CI |
| Контракты (`architecture.md`, раздел 9) | обе стороны контракта |

Чего не делать, чтобы Claude не попал в contributors:
- не просить `@claude` в GitHub что-то закоммитить;
- не давать GitHub Action Claude права на запись.

Коммиты от GitHub-приложения идут от `claude[bot]` и попадают в contributors. Ревью через Action только оставляет комментарии (права `contents: read`) и на contributors не влияет.

## Definition of Done

- [ ] Все коммиты из задачи; каждый проходит линтер и тесты.
- [ ] Тесты на новую логику. Бэкенд — pytest, фронт — vitest, сценарии — Playwright (с этапа 3).
- [ ] Критерии «Готово, когда» проверены руками или тестом.
- [ ] Контракты не менялись или обновлены отдельным коммитом (`architecture.md` + `openapi.json`).
- [ ] `/code-review` пройден, PR одобрен ревьюером, CI зелёный (включая `no-ai-attribution`).
- [ ] Нет секретов, персональных данных, `print`/`console.log`, закомментированного кода.
- [ ] Для промптов: в PR приложены результаты eval до/после.
