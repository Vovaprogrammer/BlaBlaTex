# ИИ, шаблонный модуль и MCP — задачи

**Зона:**
- `backend/app/modules/agent`: LLM-провайдеры, агент, промпты, описание картинок;
- `tools/llm-bench/`, `eval/`, `mcp/`.

**Перед любой задачей** агент читает `AGENTS.md`, `docs/architecture.md` (разделы 8 и 9.4 — всегда, остальное по «Контексту») и `docs/tasks/README.md`.

**Граница с бэкендом.** Здесь — всё, где вызывается модель. Шаблоны, материалы, чат, прогоны, блокировки, учёт токенов и детерминированные проверки делает бэкенд (`backend.md`). Встречаемся в точках входа из B2.1: бэкенд вызывает `run_agent` и `describe_image`, а зона ИИ их реализует. Задачи без LLM перенесены в бэкенд: A1.2 → B1.7, A1.3 → B2.7, A1.1 коммит 3 → B3.1, A2.1 коммит 3 → B2.6, A2.4 коммиты 1 и 3 → B2.7 и B2.5, A3.3 коммит 1 → B3.5.

Общие правила зоны:
- В тестах — только тестовая модель PydanticAI, `FakeProjectTools` и фейк `RunEvents` из B2.1, никаких сетевых вызовов к провайдерам.
- API PydanticAI и MCP SDK проверяй по документации установленной версии: они меняются.
- Промпты — файлы в `backend/app/modules/agent/prompts/`. Любое изменение промпта — отдельный коммит, в PR — результаты eval до и после.
- Агент не выдумывает факты. Числа, результаты и вывод программ — только из материалов; источники — только из инструментов поиска.
- Реальные методички и отчёты студентов не попадают в репозиторий. Eval читает их из `EVAL_DATA_DIR` вне репозитория.

### A3.5 Надёжность прогона агента
**Ветка:** `fix/a3.5-agent-run-robustness` · **Зависит от:** A2.1, A1.1 · **Контекст:** 8, 9.4

Находки сквозной проверки этапа 2 (PR #68). Из-за них прогон обрывается или студент видит не ту причину ошибки.

**Коммиты:**
1. `fix(llm): limit chunk wait, not the whole streamed reply` — в `backend/app/modules/agent/models.py` `request_timeout` равен `timeout` провайдера (по умолчанию 30 с), а в pydantic-ai 2.66 он ограничивает весь потоковый ответ до последнего куска. Длинная правка раздела обрывается, и студент видит «Модель сейчас недоступна». Ограничивать ожидание очередного куска и первого события (`timeout`, `first_event_timeout`), а общий срок ответа сделать отдельной настройкой с большим значением.
2. `fix(agent): own request limit and its own message` — в `runner.py` `UsageLimits` оставляет `request_limit=50` по умолчанию, и при его превышении студент видит «Превышен лимит токенов прогона». Нужны свой лимит запросов в настройках и своё сообщение. Заодно проверить лимит 200 000 токенов: он суммарный по всем запросам прогона, а в живых прогонах уходило 45–110 тыс.
3. `fix(agent): send screenshots to the vision model` — `get_image` в `tools.py` отдаёт скриншот модели `main`, роль `vision` не используется. Если `main` не принимает картинки, провайдер отвечает 400, и падает весь прогон.
4. `fix(agent): ignore extra tool arguments in one place` — сейчас (B2.9) лишние аргументы пропускают только инструменты без параметров (`**_ignored`). `read_file`, `edit_file` и другие лишний ключ по-прежнему отвергают и тратят повторы. Нужно общее решение в одном месте; оно же убирает `TypeError`, если модель передаст аргумент с именем `ctx`.
5. `fix(agent): keep model output out of failure logs` — `_describe` в `runner.py` пишет `UnexpectedModelBehavior.message`, а там бывают значения от модели, например имя несуществующего инструмента.
6. `fix(agent): price usage by model family and provider` — `_usage` ищет цену по точному имени модели. Имя с версией в ответе (`gpt-4o-2024-08-06` вместо `gpt-4o`) или один `base_url` у основного и резервного провайдера дают стоимость 0. Там же `assert` в `_call` (`tools.py`) заменить явной проверкой.

**Готово, когда:** на каждый пункт есть тест на тестовой модели; живой прогон с длинной правкой раздела не обрывается.
