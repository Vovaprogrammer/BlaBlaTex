# BlaBlaTex на сервере вуза

Инструкция для администраторов. Студенту, который ставит BlaBlaTex себе, — [`docs/install.md`](install.md).

BlaBlaTex — это несколько контейнеров Docker из готовых образов. Ставятся они одной командой, обновляются тоже одной. Наружу открыт только веб-сервер Caddy: он отдаёт сайт, пропускает `/api` к API и сам получает сертификат HTTPS.

| Сервис | Что делает | Сеть |
|---|---|---|
| `web` | Caddy: сайт, `/api`, HTTPS | порты 80 и 443 |
| `api` | REST API для сайта и агентов (MCP) | к провайдеру ИИ |
| `worker` | сборки PDF, ИИ в чате, ночная уборка файлов | к провайдеру ИИ |
| `compiler` | LaTeX в песочнице | без интернета |
| `postgres`, `redis` | база и очередь | без интернета |
| `backup` | ночной бэкап базы и файлов | без интернета |
| `init`, `migrate` | при запуске: секреты и миграции базы | — |

## Требования

По замерам на тестовом стенде (лабораторная работа, один студент):

- **Процессор** — от 2 ядер. Компилятору выделено до 2 ядер и он собирает до двух PDF сразу; лабораторная собирается за 1–2 секунды.
- **Память** — от 4 ГБ. В покое все контейнеры занимают около 0,5 ГБ, компилятору выделено до 2 ГБ.
- **Диск** — от 20 ГБ: образы около 10,6 ГБ (компилятор — полный TeX Live, около 9 ГБ), остальное — проекты студентов и бэкапы. Один проект — до 200 МБ.
- **ПО** — Linux с Docker Engine 25+ и Docker Compose 2.24+.
- **Сеть:**
  - входящие — TCP 80 и 443 (UDP 443 не нужен);
  - исходящие — `ghcr.io` (образы BlaBlaTex), `registry-1.docker.io` (Postgres и Redis), Let's Encrypt (`acme-v02.api.letsencrypt.org`, сертификат), провайдер ИИ (`base_url` из `LLM_PROVIDERS`). Если у вуза своё зеркало образов — `BBT_REGISTRY` в `.env`.

**Адрес BlaBlaTex должен открываться из всех стран**, а не только с российских адресов. Студенты подключают своего ИИ-агента (MCP), а ему из России обычно нужен VPN; с VPN запросы агента к BlaBlaTex приходят с зарубежного адреса. Защиты блок по стране здесь не добавляет: API пускает агентов только по личному токену. Подробнее — ADR 0003, «Блок по стране».

## Установка

1. Скачайте из [последнего выпуска](https://github.com/Vovaprogrammer/BlaBlaTex/releases) три файла в одну папку, например `/opt/blablatex`: `compose.yaml`, `compose.server.yaml`, `server.env.example`.
2. `cp server.env.example .env` и заполните `.env`: как минимум `BBT_DOMAIN` и провайдера ИИ (`LLM_PROVIDERS`, `LLM_DEFAULT_PROVIDER`). Для реальных данных студентов — провайдер из России (ADR 0003).
3. Домен должен указывать на сервер (запись A или AAAA), порты 80 и 443 — быть открыты.
4. В этой папке:

```bash
docker compose up -d --wait
```

Пароль базы и ключ шифрования создадутся сами при первом запуске и лягут в том `secrets`. Миграции базы применяются при каждом запуске. Сертификат Caddy получит в первые секунды — проверьте `https://<домен>`.

Версия образов — из файлов выпуска. Закрепить другую — `BBT_VERSION=2.0.0` в `.env`.

### Свой прокси вуза перед BlaBlaTex

Если HTTPS держит прокси вуза:

- в `.env`: `BBT_DOMAIN=:80` — Caddy слушает http на 80; `BBT_TRUSTED_PROXIES=<адрес прокси>/32` — только от него Caddy примет `X-Forwarded-For`;
- прокси передаёт `X-Forwarded-For` и `X-Forwarded-Proto`, ставит `Strict-Transport-Security` (раз HTTPS у него);
- не буферизует ответы и не обрывает долгие запросы: поток событий (`/api/v1/projects/*/events`) открыт часами, ожидание сборки длится до 70 секунд;
- принимает тело запроса до 210 МБ: загрузка материалов — до 200 МБ за раз.

## Обновление

1. Бэкап (ниже, «Бэкап вручную»).
2. Файлы нового выпуска — поверх старых, `.env` не трогать. Или только поменять `BBT_VERSION` в `.env`.
3. В папке установки:

```bash
docker compose up -d --wait
```

Образы скачаются, миграции применятся, данные в томах сохранятся. Откатиться на прошлую версию можно только вместе с бэкапом, снятым до обновления: миграции базы идут только вперёд.

## Бэкап

Сервис `backup` каждую ночь в `BBT_BACKUP_AT` (по умолчанию 03:00 по Москве) снимает дамп базы и копию файлов и хранит последние `BBT_BACKUP_KEEP` (по умолчанию 14) бэкапов.

- **Когда:** `BBT_BACKUP_AT` — время `ЧЧ:ММ`, например `03:00`. С другим видом сервис `backup` не запустится: проверьте `docker compose logs backup` после правки.
- **Где:** том `blablatex-app_backups` или папка из `BBT_BACKUP_DIR`. Папка на сервере должна принадлежать uid 1000: `sudo install -d -o 1000 -g 1000 /var/backups/blablatex`.
- **Что внутри:** папка `<дата_время>` с `db.dump` (pg_dump) и `storage/` — файлы студентов.
- **База и файлы подходят друг к другу:** пока идёт бэкап, удаление файлов откладывается до следующей ночной уборки, так что файл из дампа не пропадёт, пока его копируют.
- **Место:** файл, который уже есть в прошлом бэкапе, берётся жёсткой ссылкой — каждый бэкап полный, а место занимает только новое. Копируйте бэкапы на другой сервер с сохранением ссылок: `rsync -aH`.
- **Проверка:** `docker compose logs backup` — строка `backup_done` за каждую ночь, `backup_failed` — сбой.
- **Ключ шифрования в бэкап не входит** — его храните отдельно (ниже, «Ключи»).

Бэкап вручную:

```bash
docker compose run --rm backup python -m app.scripts.backup
```

### Восстановление

Только на чистую установку — до первого запуска API.

1. Файлы установки и `.env` — как при установке. В `.env` — `APP_ENCRYPTION_KEY` со старого сервера (ниже, «Ключи»).
2. Поднять только базу: `docker compose up -d --wait postgres`.
3. Положить папку бэкапа в `BBT_BACKUP_DIR` (или в том `backups`).
4. Восстановить:

```bash
docker compose run --rm backup python -m app.scripts.restore /srv/backups/<дата_время>
```

5. Запустить всё: `docker compose up -d --wait`. Миграции доведут базу до текущей версии.

Если база уже не пустая, восстановление откажется и ничего не тронет.

## Ключи

- **Ключ шифрования** (`APP_ENCRYPTION_KEY`) шифрует ключи ИИ, которые студенты сохранили на сайте. Без него эти ключи не расшифровать — студентам придётся ввести их заново. Сохраните его отдельно от бэкапов. Если `APP_ENCRYPTION_KEY` задан в `.env`, ключ — оттуда (он сильнее файла), иначе — созданный при установке:

```bash
docker compose run --rm --no-deps backup cat /run/secrets/blablatex/app_encryption_key
```

- **Смена ключа шифрования:**
  1. Новый ключ: `docker compose run --rm --no-deps backup python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.
  2. В `.env`: `APP_ENCRYPTION_KEY=<новый>,<старый>`, затем `docker compose up -d --wait`.
  3. Перешифровать: `docker compose exec api python -m app.scripts.rotate_llm_keys`. Именно в `api`: ему `.env` передаёт оба ключа, а сервису `backup` — нет.
  4. В `.env` оставить только `APP_ENCRYPTION_KEY=<новый>` и снова `docker compose up -d --wait`. Теперь ключ — в `.env`: он сильнее файла в томе `secrets`.
- **Пароль базы** снаружи не нужен: база только во внутренней сети Docker. Сменить:

```bash
NEW=$(openssl rand -hex 32)
docker compose exec -T postgres psql -U blablatex -d blablatex -c "ALTER USER blablatex PASSWORD '$NEW'"
docker compose run --rm --no-deps --entrypoint sh init -c "chmod 600 /run/secrets/blablatex/postgres_password && printf %s '$NEW' > /run/secrets/blablatex/postgres_password && chmod 444 /run/secrets/blablatex/postgres_password"
docker compose up -d --wait --force-recreate api worker backup
```

- **Ключ провайдера ИИ** — в `LLM_PROVIDERS` в `.env`; после правки — `docker compose up -d --wait`.

## Логи

```bash
docker compose logs -f api worker
```

Логи бэкенда — JSON, по строке на событие. Пароли, токены, ключи и содержимое файлов студентов в них не пишутся. У каждого сервиса хранится до 3 файлов по 10 МБ, старые удаляются сами.

## Что проверить после установки

- `https://<домен>` открывается, регистрация работает;
- `curl -sI https://<домен>/` — есть `Strict-Transport-Security` и `Content-Security-Policy`;
- `curl -s https://<домен>/api/docs` — `404`: документация API в проде закрыта, описание — `backend/openapi.json` в репозитории;
- с зарубежного адреса (через VPN) сайт тоже открывается.
