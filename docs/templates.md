# Шаблоны LaTeX

Шаблон — папка в `templates/`, из которой создаётся проект студента. Первая часть — как сделать шаблон: по ней новый шаблон делается без кода бэкенда. Вторая — класс `mtuci-report`, который оформляет любой отчёт.

## Шаблон

### Папка шаблона

```
templates/
  _shared/mtuci-report.cls     общий класс — раздел «Класс mtuci-report»
  _schema/template.schema.json схема template.yaml для редактора
  _examples/                   эталонные отчёты
  _class-test/                 тестовый документ класса
  mtuci-lab/                   шаблон лабораторной
    template.yaml              манифест: поля, разделы, указания для ИИ, проверки
    main.tex                   главный файл отчёта
    meta.sample.tex            пример meta.tex с вымышленным студентом
    sections/goal.tex …        файлы разделов
```

Имя папки шаблона — его `slug`. Папка, имя которой начинается с `_`, — не шаблон: бэкенд её пропускает, и студенту она не видна.

Что попадает в проект студента:

| Файл | В проекте | Зачем |
|---|---|---|
| `template.yaml` | нет | бэкенд читает его при старте |
| `meta.sample.tex` | нет | с ним шаблон собирается в `check-template`, в проекте вместо него `meta.tex` |
| `main.tex`, `sections/*.tex` и все остальные файлы папки | да, копией при создании проекта | исходники отчёта: дальше студент и ИИ правят свою копию |
| `meta.tex` | создаёт бэкенд | макросы `\bbt...` из профиля и полей проекта |
| класс `mtuci-report.cls` | нет | лежит в компиляторе и подключается при каждой сборке |

Файлы шаблона подчиняются тем же правилам, что файлы проекта (`architecture.md` 9.8). Нарушение — ошибка шаблона, и сервис не стартует:

| Нельзя | Сообщение бэкенда |
|---|---|
| картинки и другие нетекстовые файлы. Можно `.tex .bib .sty .cls .txt .md .csv`, данные (`.json .yaml .xml` …) и код (`.py .sql .c` …) | `шаблон может содержать только текстовые файлы: …` |
| кодировка не UTF-8 | `файл не в кодировке UTF-8` |
| файл больше 2 МБ | `текстовый файл больше 2 МБ` |
| в имени `% # ~ $ & ^ { } \ :`, `"` или обратная кавычка | например, `Символ # в имени ломает сборку LaTeX — уберите его` |
| файл `meta.tex` | `meta.tex создаёт бэкенд из профиля и полей (9.6); пример — в meta.sample.tex` |
| папка `out/` | `папка out/ занята: туда сборка пишет результаты (9.7)` |
| ссылка (symlink) на файл вне папки шаблона | `ссылка ведёт за пределы папки шаблона` |

Скрытые файлы (имя на `.`), `Thumbs.db` и `desktop.ini` пропускаются молча и в проект не попадают. Переводы строк Windows (CRLF) в проекте становятся обычными (LF).

### Ошибка в шаблоне

Бэкенд проверяет все шаблоны при старте API и воркера. Если ошибка хотя бы в одном шаблоне, не стартует ни API, ни воркер. Сообщение перечисляет все ошибки сразу:

```
Шаблоны в …/templates не прошли проверку:
- mtuci-lab/template.yaml: fields.1.key: ключ даёт макрос \bbtGroup из 9.6 — он занят
- mtuci-lab/template.yaml: sections.2.file: нет файла sections/theory.tex
```

В строке — папка и файл, путь к ошибке в `template.yaml` и причина. Номера в пути считаются с нуля: `fields.1` — второе поле, `sections.2` — третий раздел. Ошибка без пути относится к манифесту целиком. Ошибки формата пишет библиотека проверки, по-английски:

| Сообщение | Значит |
|---|---|
| `Field required` | нет обязательного ключа |
| `Extra inputs are not permitted` | лишний ключ — чаще всего опечатка в имени |
| `Input should be 'lab', 'vkr', …` | значения нет в списке допустимых |
| `Input should be a valid integer`, `… string`, `… boolean` | не тот тип: `version: "3"` вместо `version: 3`, `required: да` вместо `required: true` |
| `String should match pattern '…'` | строка не по формату; формат — в таблицах ниже |
| `String should have at least 1 character` | пустая строка |

Проверить шаблоны без запуска сервиса и без базы:

```
cd backend
uv run pytest tests/test_template_registry.py -k repository
```

Подсказки и часть ошибок показывает и редактор, прямо при вводе: первая строка `template.yaml` подключает схему (в VS Code нужно расширение YAML от Red Hat):

```yaml
# yaml-language-server: $schema=../_schema/template.schema.json
```

Схема ловит лишний ключ, неверный тип, формат и значение не из списка. Остальное проверяет только бэкенд:
- повторы ключей, разделов и проверок;
- `options` у `select` и тип `default`;
- занятые ключи полей и дисциплину, заданную дважды;
- что файлы есть и `slug` совпадает с папкой.

### template.yaml

Пример — сокращённый `mtuci-lab`:

```yaml
# yaml-language-server: $schema=../_schema/template.schema.json
slug: mtuci-lab
version: 3
kind: lab
title: "Лабораторная или практическая работа"
engine: xelatex
main: main.tex
fields:
  - key: discipline
    label: "Дисциплина"
    type: string
    required: true
  - key: lab_number
    label: "Номер работы"
    type: int
    required: true
  - key: teacher
    label: "Преподаватель (например, доц. Петров П. П.)"
    type: string
  - key: work_type
    label: "Вид работы"
    type: select
    options: ["Лабораторная работа", "Практическая работа"]
    default: "Лабораторная работа"
sections:
  - id: goal
    title: "Цель работы"
    file: sections/goal.tex
    required: true
    guide: >-
      1–2 предложения: цель из методички или задания, близко к тексту источника. Цели в
      материалах нет — раздел не заполнять, а в чате попросить методичку.
  - id: theory
    title: "Теоретическая часть"
    file: sections/theory.tex
    guide: >-
      Необязательный, по умолчанию не заполнять. Только если теорию требует методичка или
      просит студент: до страницы своими словами о том, на что опирается ход работы.
ai_rules: |
  Шрифты, отступы, пакеты, \newpage и \vspace не задавать — это делает класс mtuci-report.
  \bbtScreenshot и \bbtCodeFile — команды, не окружения.
checks:
  - build-failed
  - section-empty
```

Шаблон целиком:

| Ключ | Обязательный | Что это | Если неверно |
|---|---|---|---|
| `slug` | да | имя папки шаблона: строчная латиница и цифры через `-`, до 100 символов, например `mtuci-lab`. По нему проект помнит свой шаблон | `slug: … не совпадает с именем папки`; заглавные буквы или `_` — `String should match pattern` |
| `version` | да | целое число от 1, при каждом изменении шаблона +1. Проект запоминает версию, из которой создан; на сборку и проверки она пока не влияет | `"3"` в кавычках — `Input should be a valid integer`; `0` — `Input should be greater than or equal to 1` |
| `kind` | да | вид работы: `lab`, `vkr`, `article` или `slides`. Проект получает его из шаблона; на сборку и проверки он пока не влияет | `Input should be 'lab', 'vkr', 'article' or 'slides'` |
| `title` | да | название шаблона в списке при создании проекта | пустое — `String should have at least 1 character` |
| `discipline` | нет | дисциплина для `\bbtDiscipline`, если шаблон для одного предмета. Нет её — дисциплину вводит студент (см. «Дисциплина») | задана и здесь, и полем — `дисциплина задана и в шаблоне, и полем discipline` |
| `engine` | да | движок: `xelatex` или `pdflatex`. Класс `mtuci-report` работает только с XeLaTeX, и `check-template` собирает только им, поэтому пишите `xelatex` | `Input should be 'xelatex' or 'pdflatex'` |
| `main` | да | главный файл: латиница, цифры, `_ . / -`, на `.tex`. `check-template` собирает только `main.tex`, поэтому пишите его | нет файла — `main: нет файла …`; пробел или кириллица — `String should match pattern` |
| `fields` | нет | поля, которые студент заполняет при создании проекта, — таблица «Поле проекта». Нет списка — полей нет | ошибки отдельного поля — с путём `fields.N.…` |
| `sections` | нет | разделы отчёта — таблица «Раздел». По ним ИИ знает, что и в какой файл писать, а проверки — какие разделы обязательны | ошибки отдельного раздела — с путём `sections.N.…` |
| `ai_rules` | нет | правила для ИИ на весь отчёт («Указания для ИИ»). В интерфейсе студент их не видит | не строка — `Input should be a valid string` |
| `checks` | нет | проверки отчёта — id из [checks.md](checks.md), часть 1, без повторов. Нет списка — у шаблона проверок нет («Проверки отчёта») | опечатка в id — `Input should be 'build-failed', …`; повтор — `проверка … повторяется` |

Поле проекта — элемент списка `fields`. Студент заполняет поля в форме при создании проекта и потом в «Данных работы». Каждое поле даёт макрос `\bbt<Key>` в `meta.tex`.

| Ключ | Обязательный | Что это | Если неверно |
|---|---|---|---|
| `fields[].key` | да | имя поля: слова из строчных латинских букв через одиночный `_`, до 50 символов. Из него получается макрос: `lab_number` → `\bbtLabNumber`. Цифры нельзя: `\bbtLab2` TeX прочтёт как `\bbtLab` и «2». Заняты ключи встроенных макросов: `last_name`, `first_name`, `middle_name`, `short_name`, `full_name`, `group`, `faculty`, `department`, `year`, `city`, `title_page`, `screenshot`, `code_file` | `lab2` — `String should match pattern`; занятый ключ — `ключ даёт макрос \bbtGroup из 9.6 — он занят`; повтор — `ключ поля … повторяется` |
| `fields[].label` | да | подпись в форме, понятная студенту. Пример значения — в скобках: «Преподаватель (например, доц. Петров П. П.)» | пустая — `String should have at least 1 character` |
| `fields[].type` | да | `string` — строка до 200 символов, `text` — несколько строк до 10 000 символов, `int` — целое число, `select` — выбор из `options` | `Input should be 'string', 'int', 'text' or 'select'` |
| `fields[].required` | нет | `true` — без значения проект не создать. По умолчанию `false` | `да` вместо `true` — `Input should be a valid boolean` |
| `fields[].options` | нет | варианты для `type: select`: непустой список без повторов, каждый до 200 символов. У других типов `options` нет | `у поля type: select нужен непустой список options`; `options бывают только у поля type: select`; `варианты в options повторяются` |
| `fields[].default` | нет | значение по умолчанию: форма подставляет его заранее, и оно сохраняется, если поле не передали. Того же типа, что поле, у `select` — один из `options`, не длиннее лимита типа | `у поля type: int default должен быть числом`; `default должен быть одним из options`; `у поля type: string default длиннее 200 символов` |

Раздел — элемент списка `sections`, в порядке отчёта:

| Ключ | Обязательный | Что это | Если неверно |
|---|---|---|---|
| `sections[].id` | да | короткое имя раздела: строчная латиница, цифры и `_`, с буквы, например `goal` | `Goal` — `String should match pattern`; повтор — `id раздела … повторяется` |
| `sections[].title` | да | название, как в отчёте: «Цель работы». Его видят ИИ и студент в находке `section-empty` | пустое — `String should have at least 1 character` |
| `sections[].file` | да | файл раздела в папке шаблона, на `.tex`, например `sections/goal.tex`. Подключается в `main.tex` через `\input` | нет файла — `sections.N.file: нет файла …`; не `.tex` — `String should match pattern '\.tex$'`; повтор — `файл раздела … повторяется` |
| `sections[].required` | нет | `true` — раздел не может остаться пустым или пропасть из отчёта, иначе находка `section-empty`. По умолчанию `false` | `да` вместо `true` — `Input should be a valid boolean` |
| `sections[].guide` | нет | что писать в разделе — для ИИ («Указания для ИИ») | не строка — `Input should be a valid string` |

Как писать YAML:
- Длинный текст (`guide`, `ai_rules`) — блоком. После `>-` строки склеиваются в один абзац, после `|` и `|-` переводы строк сохраняются — так пишут списки. В блоке обратные слэши пишутся как есть: `\bbtCodeFile`. В строке в двойных кавычках их удваивают: `"\\bbtCodeFile"`.
- Строки с `:`, `#` и кавычками берите в двойные кавычки: `title: "Лабораторная работа: вариант"`.
- Типы строгие: `version: "3"` и `default: 3` у строкового поля — ошибка. Да и нет — `true` и `false`.
- Повтор ключа — ошибка с номером строки: `строка 5: ключ version повторяется`.

### Поля проекта и meta.tex

`meta.tex` создаёт бэкенд в корне проекта из профиля студента и полей проекта. Студент и ИИ его не правят: он пересоздаётся при каждом изменении профиля или полей. Файлы шаблона берут данные студента и работы только из его макросов:

| Макрос | Откуда |
|---|---|
| `\bbtLastName`, `\bbtFirstName`, `\bbtMiddleName` | профиль: части ФИО |
| `\bbtShortName`, `\bbtFullName` | профиль: «Фамилия И. О.» и полное ФИО |
| `\bbtGroup`, `\bbtFaculty`, `\bbtDepartment` | профиль: группа, факультет, кафедра |
| `\bbtDiscipline` | `discipline` из `template.yaml` или поле `discipline` проекта |
| `\bbtYear`, `\bbtCity` | год сборки и «Москва» |
| `\bbt<Key>` | поле шаблона: `lab_number` → `\bbtLabNumber`, `work_type` → `\bbtWorkType` |

- Значения экранированы: `& _ % # $ { } ~ ^ \` печатаются как есть.
- Значение — в одну строку. Абзацы сохраняются только у поля `type: text`.
- Пустое поле — пустой макрос, сборка не падает. Встроенные макросы и поля титульного листа класс заранее объявляет пустыми: `\bbtVariant` есть, даже если в шаблоне нет поля `variant`.

**Дисциплина.** Если шаблон для одного предмета, она задаётся в `template.yaml`: `discipline: "Структуры и алгоритмы обработки данных"`. Если шаблон один на все предметы, как `mtuci-lab`, ключа `discipline` в манифесте нет, а студент вводит её в поле с `key: discipline`. Значение этого поля попадает в `\bbtDiscipline`, всегда одной строкой, и ИИ получает ту же дисциплину, что на титуле. Задать дисциплину и там, и там нельзя. `discipline: ""` тоже считается заданной.

**Одинаковые поля — с одинаковыми ключами.** Поля с тем же смыслом, что в `mtuci-lab`, называйте теми же ключами:
- `\bbtTitlePage` печатает `lab_number`, `lab_title`, `variant`, `teacher` и `work_type` («Титульный лист»), а проверка `title-empty` предупреждает о пустых `lab_number`, `lab_title` и `teacher`;
- у этих ключей в форме создания проекта свои подсказки с примерами, у остальных — общая подсказка по типу поля.

Титульный лист класса сделан под лабораторную и практическую работу. Шаблону другого вида работы нужен свой титул.

**meta.sample.tex** — пример `meta.tex` с вымышленным студентом. С ним шаблон собирают `check-template` и эталоны, в проект он не копируется. Формат — как у настоящего `meta.tex`: `\def\bbtGroup{БВТ0000}`. В нём задан каждый макрос, который создаст бэкенд: все встроенные из таблицы и по одному на каждое поле, кроме `discipline` — оно даёт `\bbtDiscipline`. Данные только вымышленные.

Если в файлах шаблона есть макрос, которого нет в `meta.sample.tex`, `check-template` упадёт на `Undefined control sequence`. Обратное не ловится: макрос из `meta.sample.tex`, который бэкенд не создаст, сломает сборку у студента. Поэтому после каждого изменения ключей сверяйте `meta.sample.tex` с `fields`.

### Разделы и main.tex

```latex
\documentclass{mtuci-report}
\input{meta}
\begin{document}
\bbtTitlePage
\input{sections/goal}
\input{sections/task}
\input{sections/progress}
\input{sections/conclusion}
\end{document}
```

- Каждый файл из `sections` подключён через `\input` в порядке отчёта. При старте это не проверяется: раздел, который забыли подключить, ИИ заполнит, но в PDF его не будет. У обязательного раздела студент увидит находку `section-empty` «Раздела … нет в отчёте».
- Файл раздела начинается с `\section{…}` с тем же названием, что `title`. Под ним — комментарий для студента о том, что писать. В PDF комментарий не попадает, и `section-empty` считает такой раздел пустым.
- Подразделы ИИ пишет сам по `guide`, в шаблоне их нет.
- Пакеты оформления в `main.tex` не подключаются: оформление задаёт класс. Данные студента берутся только из макросов `meta.tex`.
- Список источников, если он нужен, — `thebibliography` в конце `main.tex`.

#### Необязательный раздел

Раздел с `required: false` в `template.yaml` подключён в `main.tex` через `\input`, но строка с `\section` в его файле закомментирована. Пока раздел не нужен, в PDF его нет, а проверка `section-empty` его не требует. Когда раздел нужен, ИИ или студент убирает `%` перед `\section`.

В `mtuci-lab` обязательные разделы — «Цель работы», «Задание», «Ход работы» и «Выводы». Необязательные — «Теоретическая часть» (после «Задания») и «Ответы на контрольные вопросы» (последним).

### Указания для ИИ

`guide` разделов и `ai_rules` ИИ получает в каждом запросе к модели, вместе со своим промптом и списком макросов класса. Шаблон в промпте выглядит так:

```
### Шаблон проекта

Лабораторная или практическая работа. Главный файл: `main.tex`.
Дисциплина: Структуры и алгоритмы обработки данных.

- Цель работы — `sections/goal.tex` (обязательный раздел). 1–2 предложения: цель из методички…
- Теоретическая часть — `sections/theory.tex`. Необязательный, по умолчанию не заполнять…

### Правила шаблона

<ai_rules>

### Макросы класса

- `\bbtScreenshot[width]{path}{caption}{label}` — Рисунок с подписью «Рисунок N — caption».
```

Агенты по токену получают то же из справки шаблона (`GET /projects/{pid}/template-guide`, [api.md](api.md)). Отсюда три правила:
- **Коротко.** Текст шаблона повторяется в каждом запросе: у `mtuci-lab` это 4 753 знака, а отчёт пишется за 20–25 запросов. Каждая лишняя строка тратит квоту студента.
- **`guide` — продолжение строки с названием раздела.** Законченные предложения с заглавной буквы, без заголовков.
- **Без повторов.** Промпт агента уже требует брать факты только из материалов, читать файл перед правкой и не трогать `meta.tex` (`backend/app/modules/agent/prompts/`). Сигнатуры макросов класса агент получает списком. Повтор не делает правило сильнее, только дороже.

#### Что куда

| Куда | Что | Пример из `mtuci-lab` |
|---|---|---|
| `guide` раздела | что обязательно в разделе, объём, чего в нём не писать, как разбирать материалы разного вида | «Выводы»: «1–2 абзаца по цели работы: что сделано и что показали результаты, с главными числами из хода работы. Без новых фактов и чисел…» |
| `ai_rules` | правила на весь отчёт, которые модель нарушает: обращения к студенту, ссылки, запись чисел, ловушки LaTeX | «Числа — с запятой и в удобных единицах (20,4 мкс, а не 2.04e-05)» |
| класс `mtuci-report` | оформление: шрифты, поля, подписи, нумерация. В правилах — только запрет задавать его вручную | «Шрифты, отступы, пакеты, \newpage и \vspace не задавать» |
| [report-formatting.md](requirements/report-formatting.md) | нормы оформления для людей и проверок. В шаблон — только то, что модель путает | кавычки «ёлочки», «с», а не «сек» |
| проверка из `checks` | то, что ловится автоматически | `ref-broken` — ссылка на несуществующую метку, `missing-glyph` — символ без шрифта |

Особенности предмета в шаблон не пишут: шаблон один на много дисциплин, а методичку и задание ИИ читает в материалах студента. Различия видов работ — в `guide` того раздела, где они видны. «Ход работы» в `mtuci-lab` разобран по пяти группам: программы и инструменты, алгоритмы с замерами, логика и автоматы, расчёт и моделирование, настройка по шагам.

#### Как писать

- **Проверяемо.** Выполнение правила видно по тексту отчёта: число, объём, конкретная запись. «Пиши подробно и грамотно» и «оформи по ГОСТ» не проверит ни модель, ни вы.
- **Что делать вместо.** Запрет без замены модель обходит. Не «не выдумывай результаты», а «нет вывода программы — пункт без результата и без утверждений о нём; какой файл загрузить — только в чате».
- **Где правило действует.** Слишком общее правило модель применяет и там, где оно ломает отчёт: пример с `\_` ниже.
- **Умолчание — явно.** «Необязательный» модель читает как «желательный». Пишите «по умолчанию не заполнять. Только если…».
- **Пример там, где ошибаются.** Сигнатуру макроса модель путает — дайте строку целиком: `\bbtScreenshot[0.8\linewidth]{materials/....png}{Подпись}{fig:...}`.
- **Одно правило — одна строка** `ai_rules`. Так правило проще найти и поправить по итогам прогона.

#### Плохо → хорошо: живые прогоны

Указания `mtuci-lab` правили по живым прогонам агента на материалах лабораторной по сортировкам и по SQL (T2.3, PR #97, issue #93 и #94):

| Было | Что вышло в отчёте | Стало | Итог |
|---|---|---|---|
| «Ход работы»: «что и как сделано… Под каждым фрагментом — пояснение, что делает этот код» | «графики и числовые результаты формируются автоматически» вместо сравнения наклонов с n² и n log n | «В пункте с результатами — что показали числа и почему: сравнение с ожиданием… а не рассказ о том, как устроена программа» и чем мерить рост времени | «при удвоении n время растёт в 2 и в 4 раза», наклоны ≈1 и ≈2 |
| «без обращений к студенту и пометок вроде «результаты нужно получить»» | «приложите вывод» в тексте отчёта | «…и фраз о том, чего нет в материалах («результаты нужно получить», «приложите вывод»)… какой файл загрузить — только в чате» | в следующих прогонах обращений нет |
| `\bbtScreenshot[ширина]{…}{…}{…}` без примера | неверный необязательный аргумент, сборка падает, а каждая лишняя сборка — запрос с полным контекстом | строка-пример `\bbtScreenshot[0.8\linewidth]{materials/....png}{Подпись}{fig:...}` | в трёх прогонах после правки макрос верный |
| «Имена из кода в тексте — \texttt{...}, «_» — \_» | `\_` в `\label` — сборка падает | «…«_» — \_ (в \label, \ref и путях — без \)» | отчёт собрался с первой попытки |
| правила о числах нет | `2.04e-05`, «сек» | «Числа — с запятой и в удобных единицах (20,4 мкс, а не 2.04e-05)… «с», «мс», не «сек»» | запятая и «с»; но встречается «0,00033 с» вместо «0,33 мс» |

**Правило — не гарантия.** В одном прогоне модель написала `\geqslant` вопреки прямому запрету. В другом выдумала вывод программы `self_check: OK`, хотя правило запрещает утверждать о результате без вывода в материалах. Указание шаблона снижает частоту ошибки, но не исключает её. Что ловится автоматически, должна ловить проверка: сборку — `build-failed`, символ без шрифта — `missing-glyph`, число не из материалов — `number-not-in-materials`. По одному прогону выводов не делают: модель ведёт себя по-разному от прогона к прогону. Надёжно сравнить два варианта правил может только eval (A2.5).

### Проверки отчёта

`checks` — какие проверки из [checks.md](checks.md) (часть 1) находят ошибки в отчёте по шаблону. Пустой список — у шаблона проверок нет. Шаблон перечисляет свои проверки сам: правила отчёта по лабораторной подходят не всякой работе. `mtuci-lab` включает все проверки части 1. Новый шаблон берёт те, чьё правило в `checks.md` верно для его вида работы. Например, `title-empty` смотрит поля титула лабораторной.

### Проверка шаблона

1. **Бэкенд принимает шаблон.** База не нужна:
   ```
   cd backend
   uv run pytest tests/test_template_registry.py -k repository
   ```
   Ошибки выводятся списком, как при старте сервиса («Ошибка в шаблоне»).
2. **Шаблон собирается** — с `meta.sample.tex` вместо `meta.tex`, тем же компилятором, что у студентов:
   ```
   docker compose up -d
   docker compose run --rm compiler check-template templates/<slug>
   ```
   Команда выводит `OK: … собран за N мс` или строки ошибок из лога LaTeX. `check-template` собирает `main.tex` движком XeLaTeX и `template.yaml` не читает. Класс compose берёт из `templates/_shared`, поэтому правка класса видна сразу, без пересборки образа.
3. **Эталоны не сломались** — после правки шаблона, класса или указаний (`docker compose up -d`):
   ```
   cd backend
   uv run pytest tests/test_template_examples.py
   uv run pytest tests/test_template_examples.py -m compiler
   ```
4. **Тесты бэкенда** — `uv run pytest` в `backend`. Часть проверок отчёта тестируется на файлах `mtuci-lab`. Нужны `docker compose up -d` и `.env`.
5. **Живой прогон ИИ.** API и воркер читают шаблоны только при старте. После правки `template.yaml` перезапустите API (`uv run fastapi dev app/main.py`) и пересоздайте воркер: `docker compose up -d --force-recreate worker`. Создайте проект из шаблона, загрузите обезличенные материалы настоящей работы и попросите ИИ сделать отчёт. Сверьте отчёт с указаниями и находками проверок. Настоящие методички и отчёты студентов в репозиторий не коммитятся.

### Эталонные отчёты

Как выглядит хороший отчёт по `mtuci-lab` для разных видов работ, показывают вымышленные эталоны в `templates/_examples/`: алгоритмы с замерами, база данных, цифровая логика, расчёт цепи, настройка сети. Устройство и проверка — в `templates/_examples/README.md`. ИИ эталоны не получает: образец в каждом запросе стоил бы слишком дорого.

Эталоны есть только у `mtuci-lab`, и тест сверяет их с ним: `main.tex` эталона совпадает с `main.tex` шаблона. Эталоны нового шаблона потребуют правки теста `backend/tests/test_template_examples.py`.

### Изменение шаблона, у которого есть проекты

Проект копирует файлы шаблона один раз, при создании. Указания, разделы, поля и проверки он берёт из текущего шаблона при каждом обращении.

| Что меняю | Что будет со старыми проектами |
|---|---|
| `main.tex`, файлы разделов и другие файлы шаблона | ничего: новые файлы получат только новые проекты |
| `guide`, `ai_rules`, `title` разделов | ИИ сразу работает по новым указаниям |
| новый раздел, другие `id` или `file` раздела | ИИ видит новый список разделов, а `main.tex` проекта старый. Файл нового раздела ИИ создаст, но в PDF его не будет. Обязательный раздел даст находку «Раздела … нет в отчёте» |
| `required` разделов, `checks` | проверки сразу идут по-новому |
| новое поле | файлы проекта его макрос не используют. Обязательное поле без `default` студенту придётся заполнить при следующем сохранении «Данных работы» |
| ключ поля переименован или удалён | форма «Данных работы» старое значение не покажет, и после сохранения оно пропадёт. При правке профиля `meta.tex` пересоздаётся без старого макроса: если файлы проекта его используют, а класс не объявляет, сборка упадёт с `Undefined control sequence` |
| `options` у `select` | старое значение остаётся до правки «Данных работы». Если его нет в новом списке, форма подставит `default` или пустое значение |
| `slug` переименован или шаблон удалён | у проекта нет шаблона: ИИ работает без указаний шаблона, «Данные работы» не сохранить, `meta.tex` не обновляется при правке профиля |
| класс `mtuci-report.cls` | вид всех отчётов меняется при следующей сборке. Поэтому макросы класса только добавляются («Класс mtuci-report») |

Отсюда правила:
- `slug`, ключи полей, `id` и `file` разделов не переименовываются и не удаляются — только добавляются новые;
- указания действуют на старые проекты сразу — проверяйте их живым прогоном до мёржа;
- при каждом изменении шаблона `version` растёт на 1.

### Новый шаблон по шагам

1. Скопируйте `templates/mtuci-lab` в `templates/<slug>`. В `template.yaml` — новый `slug` по имени папки и `version: 1`.
2. Поля: уберите лишние, добавьте свои. Поля с тем же смыслом, что в `mtuci-lab`, — с теми же ключами.
3. Разделы: на каждый раздел — файл с `\section{…}` и комментарием для студента. Подключите все файлы в `main.tex` в порядке отчёта.
4. `guide` каждого раздела и `ai_rules` — по «Указаниям для ИИ».
5. `checks` — проверки, чьи правила подходят к виду работы.
6. `meta.sample.tex` — вымышленный студент: встроенные макросы и по макросу на каждое поле.
7. Проверка: бэкенд, `check-template`, тесты бэкенда («Проверка шаблона»).
8. Живой прогон ИИ на обезличенных материалах настоящей работы.

Если шаблону нужен другой титульный лист или оформление, нужны новые макросы класса («Класс mtuci-report»). Существующие макросы при этом не меняются.

## Класс mtuci-report

Общий класс всех учебных отчётов МТУСИ: `templates/_shared/mtuci-report.cls`. Оформление — по [report-formatting.md](requirements/report-formatting.md). Стиль один на весь вуз, параметров у класса нет.

Класс сам задаёт:
- поля 30/10/20/25 мм;
- Liberation Serif 14 pt, полуторный интервал (30 строк на странице), абзацный отступ 1,25 см, выравнивание по ширине;
- номера страниц внизу по центру; на титульнике номера нет;
- оформление и нумерацию заголовков, подписей, формул, перечислений, списка источников и приложений.

В тексте отчёта шрифты, поля, интервалы и отступы не задаются. Пакеты оформления не подключаются.

### Документ

```latex
\documentclass{mtuci-report}
\input{meta}
\begin{document}
\bbtTitlePage
\input{sections/goal}
...
\end{document}
```

`meta.tex` создаёт бэкенд: макросы `\bbt...` из профиля и полей проекта (`architecture.md` 9.6). Класс заранее объявляет их пустыми. Если какого-то макроса в `meta.tex` нет, на его месте пусто, а сборка не падает.

### Макросы класса

| Макрос | Что даёт |
|---|---|
| `\bbtTitlePage` | титульный лист из `meta.tex` |
| `\bbtScreenshot[ширина]{путь}{подпись}{метка}` | рисунок с подписью «Рисунок 1 – подпись» под ним |
| `\bbtCodeFile[язык, lines=10-25]{путь}{подпись}{метка}` | листинг из файла — весь или строки с 10-й по 25-ю, подпись «Листинг 1 – подпись» над ним |
| `\begin{bbtcode}{язык}{подпись}{метка}` … `\end{bbtcode}` | листинг текстом |
| `\begin{bbttable}{подпись}{метка}` + `tabular` | таблица с подписью «Таблица 1 – подпись» над ней |
| `\begin{bbttask}[нумерация]` + `\item` … `\end{bbttask}` | пункты задания с номерами из методички: «1)», «2)», с `[а]` — «а)», «б)» |

Общее для всех:
- номер в подписи ставит класс: сквозной по работе — «1», «2», …; в приложении А — «А.1», в подразделе приложения — «А.1.2»;
- подпись пишется с прописной буквы, без точки в конце;
- метка нужна для ссылки `\ref{метка}`, её можно оставить пустой `{}`;
- на каждый рисунок, таблицу и листинг в тексте есть ссылка, она стоит до них.

**Рисунок.** Ширина — длина LaTeX, по умолчанию ширина текста. Выше 2/3 страницы рисунок не бывает, пропорции сохраняются. Он встаёт сразу после ссылки, а если места нет — наверху следующей страницы, и в чужой раздел не уходит. Форматы — PNG, JPG и PDF; SVG не вставляется.

```latex
Окно программы показано на рисунке~\ref{fig:window}.
\bbtScreenshot{materials/screen1.png}{Окно программы после запуска}{fig:window}
\bbtScreenshot[0.6\linewidth]{materials/schema.png}{Схема базы данных}{fig:schema}
```

**Листинги.** Liberation Mono 10 pt в тонкой рамке, с цветной подсветкой, без номеров строк. Кириллица в комментариях и строках печатается как есть. Длинная строка переносится у последнего пробела, продолжение — с тем же отступом и серой стрелкой.

В лабораторной код идёт фрагментами: в пункте хода работы — функция, о которой речь, под ней пояснение. Фрагмент берётся из файла нужными строками, `lines=первая-последняя` (нумерация с 1, обе включительно), — так код в отчёте точно совпадает с программой. Фрагмент — до ~40 строк; длиннее — несколько фрагментов по функциям.

Язык подсветки — первым в квадратных скобках: `python`, `c`, `c++`, `c#`, `java`, `js`, `ts`, `kotlin`, `go`, `rust`, `sql`, `php`, `pascal`, `bash`, `html` и другие; регистр не важен. Можно не указывать: язык берётся по расширению файла. Неизвестный язык или опечатка — листинг без подсветки и предупреждение в логе, сборка не падает.

```latex
Сортировка вставками приведена в листинге~\ref{lst:insert}.
\bbtCodeFile[python, lines=54-73]{materials/sort.py}{Сортировка вставками}{lst:insert}
Внешний цикл берёт очередной элемент, внутренний сдвигает большие элементы вправо…

\bbtCodeFile[lines=12-20]{materials/main.cpp}{Чтение входных данных}{lst:input}

\begin{bbtcode}{sql}{Запрос к таблице заказов}{lst:orders}
SELECT id, total FROM orders WHERE total > 1000; -- заказы дороже 1000 рублей
\end{bbtcode}
```

Код в `bbtcode` начинается со следующей строки после `\begin{bbtcode}{…}{…}{…}`. Строка `\end{bbtcode}` пишется с начала строки.

**Таблица.** Внутри — один обычный `tabular`. В окружение `table` таблицу не оборачивают, иначе сборка упадёт. Таблица стоит там, где написана, и может перейти на следующую страницу. Тогда над продолжением слева печатается «Продолжение таблицы 1», а под ним повторяется шапка — первая строка таблицы вместе с линиями сразу под ней. Подпись — 14 pt, сама таблица — 12 pt. Сначала строка-шапка, потом данные.

```latex
Результаты замеров приведены в таблице~\ref{tab:time}.
\begin{bbttable}{Время сортировки массивов}{tab:time}
  \begin{tabular}{|r|c|c|}
    \hline
    Длина массива & Слиянием, мс & Встроенная, мс \\ \hline
    1000  & 0,2 & 0,1 \\ \hline
    10000 & 2,5 & 2,3 \\ \hline
  \end{tabular}
\end{bbttable}
```

**Задание.** Пункты задания нумеруются так же, как в методичке, чтобы ход работы ссылался на те же номера. По умолчанию — цифрами, `[а]` — буквами. Если варианту достались не все пункты, номер пишется у пункта: `\item[5]`, следующий `\item` — 6. Ссылка — номер без скобки.

```latex
\begin{bbttask}
  \item реализовать сортировку вставками;\label{task:insert}
  \item[5] сравнить время работы со встроенной сортировкой.\label{task:compare}
\end{bbttask}
...
\subsection{Сравнение со встроенной сортировкой (пункт~\ref{task:compare})}
```

Выходит «1) реализовать…», «5) сравнить…» и заголовок «3.2 Сравнение со встроенной сортировкой (пункт 5)».

### Обычный LaTeX: как выглядит

| Что пишем | Что получается |
|---|---|
| `\section{Цель работы}` | «1 Цель работы» — полужирный, с абзацного отступа. Разделы идут подряд, без новой страницы |
| `\subsection{…}`, `\subsubsection{…}` | «3.1 …», «3.1.2 …». Глубже трёх уровней не бывает |
| `\section*{Введение}` | «ВВЕДЕНИЕ» — прописными по центру, без номера |
| `\texttt{rng.randrange(lo, hi + 1)}` | код в тексте: моноширинный, по высоте строчных — как основной шрифт; переносится после `.`, `,`, `(`, `)`, `_` и похожих знаков без дефиса. Подчёркивание пишется `\_` |
| `\begin{itemize}` | пункты с «–» |
| `\begin{enumerate}` | «а)», «б)», … — когда на пункты есть ссылки; вложенный `enumerate` — «1)», «2)». Ссылка `\ref` — буква без скобки: «(пункт~\ref{it:x})» → «(пункт в)» |
| `\begin{equation}\label{eq:t} … \end{equation}` | формула по центру с номером «(1)» справа; ссылка — `\eqref{eq:t}` |
| `\[ … \]` | формула без номера, если на неё нет ссылок |
| `\cite{knuth}`, `\cite[с.~132]{knuth}` | «[1]», «[1, с. 132]» |
| `\begin{thebibliography}{9}` … `\bibitem{knuth} …` | с новой страницы «СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ», записи «1. …» в порядке первой ссылки |
| `\appendix`, затем `\section{Название}` | каждое приложение с новой страницы: «Приложение А», под ним название |

Пункты перечисления — со строчной буквы, в конце `;`, у последнего — `.`.

Пояснение обозначений — сразу после формулы, без пустой строки. Каждое обозначение — с новой строки:

```latex
\begin{equation}\label{eq:time}
  T(n) = c \cdot n \log_2 n,
\end{equation}
где $T(n)$ – время сортировки, мс;\\
$c$ – постоянная, зависящая от компьютера;\\
$n$ – длина массива.
```

Ссылка на приложение — «(приложение~\ref{app:code})», где `app:code` — метка `\label` после `\section` приложения.

### Титульный лист

`\bbtTitlePage` печатает:
- шапку вуза;
- кафедру `\bbtDepartment`;
- «ОТЧЕТ» и под ним «по лабораторной работе № `\bbtLabNumber`», «по дисциплине «`\bbtDiscipline`»», «на тему «`\bbtLabTitle`»», «Вариант `\bbtVariant`»;
- строки «Студент гр. `\bbtGroup`» — `\bbtShortName` и «Преподаватель» — `\bbtTeacher`, у каждой линия для подписи;
- внизу «`\bbtCity` `\bbtYear` г.».

Вид работы берётся из поля `work_type` (`\bbtWorkType`): «Практическая работа» → «по практической работе», иначе — «по лабораторной работе». Если поле пустое, его строка не печатается, а место остаётся. Нет группы — просто «Студент», нет преподавателя — линия без фамилии.

Трудные случаи (T2.1):
- **Длинные значения.** Кафедра, дисциплина и тема переносятся по словам и стоят по центру. Если роль и имя вместе с линией не помещаются в строку, широкая колонка блока подписей сужается и переносится по словам и после дефиса двойной фамилии, с одинарным интервалом. Короткие значения стоят одной строкой, как раньше. Титульник помещается на один лист, когда кафедра, дисциплина и тема заполнены до предела поля (200 символов), а ФИО и преподаватель длинные, но из жизни.
- **«Ё», двойная фамилия, нет отчества.** Печатаются как в профиле: «Ёлкина А. Ф.», «Петрова-Водкина А. С.». Без отчества — «Ли В.».
- **Спецсимволы.** `& _ % # $ { } ~ ^ \` в значениях печатаются как есть: `meta.tex` экранирует их сам (`backend/app/modules/templates/meta.py`). Прямые кавычки `"` шрифт печатает как ”.
- **Кавычки, точка и «Кафедра» от студента.** Кавычки «…» вокруг дисциплины и темы и слово «Кафедра» класс ставит сам. Поэтому у кафедры, дисциплины и темы на титульнике убираются:
  - внешняя пара кавычек `«…»`, `"…"`, `„…“` или `“…”` — только если внутри нет таких же кавычек;
  - точка в конце — перед закрывающей кавычкой и после неё;
  - у кафедры — слово «Кафедра» в начале (в любом регистре, можно с двоеточием), снаружи кавычек или внутри.

  Примеры:
  - кафедра `Кафедра МКиИТ` → «Кафедра «МКиИТ»», а не «Кафедра «Кафедра МКиИТ»»;
  - тема `"Методы поиска в массиве."` → «на тему «Методы поиска в массиве»».

  Кавычки внутри значения и многоточие остаются. Макросы `meta.tex` не меняются: чистится только то, что печатает титульник.

Случаи собраны в тесте `test_title_page_edge_case` (`backend/tests/test_build_compiler.py`). `meta.tex` для них создаёт тот же код, что и для проекта, а собирает настоящий компилятор:

```
cd backend
uv run pytest -m compiler -k title_page
```

Превью случаев — `docs/design/previews/t2.1-title-cases/`.

### Проверка класса

Тестовый документ со всеми элементами — `templates/_class-test/` (не шаблон, студентам не виден):

```
docker compose run --rm compiler check-template templates/_class-test
```

Макросы класса только добавляются. Существующие не переименовываются и не меняют поведение. Служебные имена внутри класса — с `@` (`\bbt@...`), поэтому они не совпадают с макросами полей `\bbt<Key>`.
