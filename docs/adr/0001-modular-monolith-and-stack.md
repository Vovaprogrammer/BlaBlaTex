# ADR 0001. Модульный монолит и технологический стек

- **Статус:** принято
- **Дата:** 2026-10-31
- **Авторы:** Чистяков Владимир
- **Подробности:** [`docs/architecture.md`](../architecture.md) — источник правды; этот ADR объясняет, почему она такая.

## Контекст

BlaBlaTex переписывается с нуля. Старая версия (тег `legacy-v0`) показала, чего нельзя повторять (`architecture.md`, раздел 14):
- эндпоинты без авторизации;
- компиляция LaTeX в контейнере с ключами и без песочницы;
- синхронный `requests` внутри `async def`;
- PDF в base64 внутри JSON;
- 26 отдельных ИИ-функций вместо одного агента с инструментами.

Условия, в которых принимается решение:
- команда — 4 студента, у каждого своя зона; разработка во многом идёт через ИИ-агентов;
- один сервер, без отдельной команды эксплуатации;
- два русла: веб-интерфейс и MCP-сервер для Claude Code и других агентов;
- сборка PDF должна быть надёжной и безопасной: пользователь присылает произвольный LaTeX;
- ИИ-агенту нужен инструментальный доступ к проекту (читать, править, собирать), а не генерация текста одним запросом.

## Решение

1. **Модульный монолит на FastAPI** (`backend/app/modules/<name>/`). У каждого модуля есть владелец. Слои: `router.py` — только HTTP, `service.py` — логика, `models.py`, `schemas.py`. В чужие таблицы — только через сервис модуля-владельца.
2. **Одно ядро — три клиента.** Операции над проектом (файлы, шаблон, профиль, материалы, сборка, проверки) используют:
   - веб-интерфейс — через REST;
   - встроенный агент — через интерфейс `ProjectTools`;
   - MCP-сервер — через тот же REST с личным токеном.
3. **Отдельный сервис компиляции** — TeX Live + latexmk, XeLaTeX, в песочнице: без секретов, без интернета, `-no-shell-escape`, `-norc`, лимиты ресурсов. Бэкенд общается с ним по HTTP во внутренней сети.
4. **Фоновый воркер Taskiq** для долгого: прогоны агента, извлечение текста, сборки.
5. **Хранилища:**
   - PostgreSQL — данные и текстовые файлы;
   - Redis — очередь и события SSE;
   - бинарные файлы — за интерфейсом `Storage`: сначала диск, потом при необходимости S3.
6. **Стек:**
   - бэкенд — Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0 async, Alembic, httpx, structlog, uv, ruff, pytest;
   - фронтенд — Vite, React 19, TypeScript strict, TanStack Query, Tailwind v4, shadcn/ui, CodeMirror 6, react-pdf;
   - ИИ — PydanticAI поверх OpenAI-совместимого API; провайдер выбирается в ADR 0002;
   - MCP — локальный stdio-сервер на Python, клиент REST API.
7. **Контракты зафиксированы явно** — раздел 9 `architecture.md` и снапшот `backend/openapi.json`, из которого фронт генерирует типы.

## Рассмотренные альтернативы

- **Микросервисы** — отдельный деплой, сеть и согласование версий на каждый модуль. Для 4 человек и одного сервера это лишняя сложность.
- **Supabase или другой BaaS, как в legacy** — нет контроля над авторизацией, песочницей компиляции и фоновыми задачами.
- **Доработка legacy** — проблемы из раздела 14 заложены в основу, проще начать заново.
- **Celery вместо Taskiq** — Celery не async, а весь бэкенд асинхронный.
- **Отдельные ИИ-функции вместо агента с инструментами** — именно так было в legacy: много промптов, нет проверки результата сборкой.

## Последствия

Плюсы:
- один деплой и одна база: простые транзакции, например перемещение папки — один UPDATE;
- общие контракты для веба, агента и MCP; MCP не дублирует бизнес-логику;
- песочница изолирует TeX, и ошибки или атаки в LaTeX не задевают API и секреты;
- долгие операции не блокируют HTTP.

Минусы и риски:
- границы модулей держатся на дисциплине (правило про чужие таблицы, ревью), а не на сети;
- монолит масштабируется целиком;
- кроме API есть ещё два собственных сервиса — worker и compiler — плюс PostgreSQL и Redis; всё это нужно поднимать и мониторить.
