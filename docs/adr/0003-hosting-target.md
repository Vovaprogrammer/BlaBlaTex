# ADR 0003. Где разворачиваем сервис

- **Статус:** принято; пересмотреть при интеграции с МТУСИ
- **Дата:** 2026-10-31; обновлено 2026-11-13 — своего стенда нет, работа через агента и блок по стране
- **Авторы:** Чистяков Владимир
- **Связано:** ADR 0002 (LLM-провайдер, задача A0.1) — этот ADR ограничивает выбор провайдера; задача B3.4 (установка одной командой и пакет для вуза); `architecture.md`, раздел 13.

## Контекст

Варианты из задачи B0.3: VPS в РФ, сервер университета, хостинг за рубежом.

Что влияет на выбор:
- **Персональные данные.** Сервис хранит email (`users`), ФИО, группу, факультет и кафедру студентов (`profiles`), а в материалах могут встретиться и другие ПД. По 152-ФЗ (п. 5 ст. 18 в редакции 23-ФЗ от 28.02.2025, действует с 01.07.2025) сбор, запись, систематизация, накопление, хранение, уточнение и извлечение ПД граждан РФ ведутся с использованием баз данных на территории РФ.
- **Передача данных LLM-провайдеру.** Если материалы с ПД уходят зарубежному провайдеру, это трансграничная передача (ст. 12 152-ФЗ), о ней оператор заранее уведомляет Роскомнадзор.
- **Деньги.** Бюджета на хостинг у команды нет; оплата зарубежных сервисов из РФ затруднена.
- **Цель.** Сервис для студентов МТУСИ; дальше планируется интеграция с университетом.

> Это инженерная оценка, а не юридическая консультация. Решение нужно проверить с юристом МТУСИ (см. «Открытые вопросы»).

## Решение

1. **Сейчас (этапы 0–2) публичного стенда нет.** Сервис запускается локально на компьютерах команды через `docker compose` — см. README, раздел «Запуск для разработки». На локальных стендах — только тестовые или обезличенные данные, как в комплектах T0.2.
2. **Целевая площадка — инфраструктура МТУСИ.** Своего публичного стенда у команды нет и не будет: проект передаётся вузу — в личный кабинет МТУСИ, на его серверы. Схема из раздела 13 `architecture.md` не меняется: один сервер, `deploy/compose.yaml` + `compose.server.yaml` и Caddy с TLS. Наша часть — B3.4: готовые образы, установка одной командой и инструкция для администраторов вуза. Тот же пакет ставится на компьютер студента — так BlaBlaTex работает до передачи вузу, например на пилоте.
3. **Зарубежный хостинг не используем:** база с ФИО и группами студентов должна находиться в РФ.
4. **LLM-провайдер (вход для ADR 0002).** Провайдер меняется через `.env` без правки кода (`architecture.md`, раздел 8), поэтому разделяем два периода:
   - **разработка** (этапы 0–2, локально, только тестовые или обезличенные данные) — допустим OpenRouter с бесплатными моделями. Ограничения:
     - лимит бесплатных моделей, по сторонним обзорам около 50 запросов в день на ключ, а один прогон агента — это 10–30 запросов;
     - пополнить баланс из РФ сейчас нельзя;
     - части команды нужен системный VPN, в том числе для запросов из Docker;
     - бесплатные модели могут сохранять запросы, поэтому реальные материалы туда не отправляем;
   - **реальные данные** (пилот этапа 3, сервер МТУСИ) — провайдер, доступный из РФ без VPN и с оплатой в рублях: из кандидатов A0.1 — Yandex AI Studio, GigaChat, российские агрегаторы с OpenAI-совместимым API. OpenRouter здесь не используем;
   - персональные данные могут попасть к модели: через инструмент `get_profile` (`architecture.md`, 9.4), чтение `meta.tex` или титульные листы в материалах. Поэтому зарубежный провайдер на реальных данных — это трансграничная передача, даже если ФИО в самом отчёте подставляются макросами `\bbt...` (9.6).

5. **Как студент работает с сервисом.** Через личный кабинет МТУСИ (сайт) или через своего ИИ-агента — Claude Code, Codex, Cursor, opencode (раздел 11 `architecture.md`). Во втором случае MCP-сервер `blablatex-mcp` работает на компьютере студента и каждым инструментом обращается к API BlaBlaTex на сервере вуза.

## Последствия

Плюсы:
- данные студентов остаются в РФ;
- расходов на хостинг нет;
- путь к официальному использованию сервиса в МТУСИ.

Минусы и риски:
- до интеграции с МТУСИ нет публичного адреса: сервис работает только там, где его установили, — на компьютере команды или студента (B3.4);
- зависимость от администраторов МТУСИ: Docker на сервере, исходящий доступ к API LLM, домен и TLS, бэкапы, время реакции на сбои;
- перед пилотом переходим с OpenRouter на провайдера из РФ: промпты и поведение агента нужно перепроверить на новой модели (eval, A2.5);
- если для реальных данных в ADR 0002 всё же выберут зарубежного провайдера, понадобится уведомление о трансграничной передаче и пересмотр этого ADR;
- **блок по стране.** Сайт и личный кабинет МТУСИ открываются только с российских адресов: проверено 2026-11-09, через VPN с выходом в Германии — 403. Агенту студента из РФ обычно нужен VPN, а MCP-сервер ходит в API BlaBlaTex с того же компьютера. Если API окажется за тем же блоком, при включённом VPN студент получит отказ. Выходы, от лучшего для студента:
  1. вуз открывает адрес BlaBlaTex для всех стран (вопрос 9.1 в `docs/requirements/questions-for-university.md`). Защиты блок здесь не добавляет: API пускает только по личному токену;
  2. раздельное туннелирование VPN: через VPN идут только запросы агента к его провайдеру ИИ, российские адреса — напрямую. Инструкция — в `docs/mcp.md` (A4.4);
  3. агент на модели провайдера из РФ — VPN не нужен;
  4. локальная установка BlaBlaTex: запросы не уходят с компьютера, но нужен Docker и около 9 ГБ на образ компилятора.

  MCP-клиент отличает такой отказ от ошибок API и говорит студенту, что делать (A4.1). Токен для агента студент создаёт на сайте — для этого VPN выключают один раз.

## Открытые вопросы

- Где проводить пилот этапа 3 (5–10 студентов), если сервер МТУСИ ещё не готов?
- Откроет ли вуз адрес BlaBlaTex для запросов из любых стран (вопрос 9.1)? Если нет — студентам с агентом понадобится раздельное туннелирование VPN.
- Кто оператор персональных данных — МТУСИ или команда? Кто подаёт уведомление в Роскомнадзор?
- Разрешён ли с сервера МТУСИ исходящий доступ к API LLM-провайдера?
- Требования МТУСИ к размещению: ОС, Docker, сеть, домен, вход через университетские учётные записи.
- Юридическая проверка решения и текста согласия на обработку ПД (T3.3).
